# Phase 10 — Investigating agent: Requirements

## Context

This is phase P10 in [roadmap.md](../../roadmap.md). Since P09, every message ends as one case with a routing decision, and people review the cases that need it. A `technical_fault` case reaches the technical team with only the classification and the enrichment: who the customer is, the area and any matching outage. Nobody has looked at the customer's line or their recent tickets yet.

This phase builds step 5 of [mission.md](../../mission.md), **investigation**: for technical faults only, a small agent with a bounded loop checks outages, line status and recent tickets, and returns a likely cause with evidence. It is the system's **one agentic step**, and it follows these principles:

- **A workflow by default, an agent only where open-ended investigation helps:** the loop has a step limit, three read-only tools and a validated output.
- **No autonomous agent that takes actions** (non-goal): the agent reads and reports. It never routes, never writes to the CRM, and can't change the team.
- **People decide the hard cases:** an inconclusive investigation sends the case to review (`investigation_inconclusive`, already listed in [tech-stack.md](../../tech-stack.md), "Routing rules").
- **Privacy by design:** the agent sees the masked text and tool results that hold no identifier values.
- **Measured, not assumed:** the evaluation reports cause accuracy on the dataset's 17 technical faults.

## Scope

In scope:

- **Line status in the mock CRM:** a new `crm_line_status` table (one row per service), generated by `npm run crm:generate` (generator `crm-generate.v2`) and loaded by `npm run crm:seed`. Each technical-fault message gets a **designed likely cause** in the seed, with line status and tickets to match (see Data).
- **The agent** in `src/pipeline/investigate.ts` (`investigate.v1`): a hand-written loop against the Anthropic API, no agent framework (see The agent).
- **The prompt** `investigate.v1` in `src/llm/prompts/`, registered in `versions.json`.
- **The LLM client** gains a multi-turn method with tools (see Decisions).
- **Storage** (migration `0009`): `investigations` (one row per attempt, never updated), `crm_line_status`, and the decision log's new `investigate` step.
- **Routing** `route.v3`: the rule `investigation_inconclusive`.
- **The pipeline runner** `process.v2`: mask → classify → enrich → **investigate** → route, resumable as before.
- **`npm run investigate -- <id>`:** investigates one stored interaction after enrichment (paid; `--dry-run` shows the request without calling the model).
- **The review screen (P09)** shows the investigation: cause, confidence, summary, evidence and the tools called.
- **Evaluation** `npm run eval:investigate` (see Evaluation).
- **Tests:** loop tests with a scripted mock client (including the step limit), tool tests, routing tests, integration tests for the migration, the tools and the runner.
- **Docs:** [tech-stack.md](../../tech-stack.md) (data model, the agent, routing, pipeline) and the README. Approving this spec approves these edits.

Out of scope (later phases):

- Running the injection set, or hardening against it (P11). This phase keeps the existing defences (escaped message, read-only tools, validated output) and adds the customer-ID guard (see Tools).
- The evaluation in CI (P12).
- The review web page (P13).
- An MCP server for the tools (P16).
- Acting on the cause: opening a ticket, notifying the customer or changing the team. The investigation is evidence for the technical team and the reviewer.
- New dataset messages. The dataset stays as it is (see Notes on `customer_equipment`).

## The agent

### When it runs

For **every case whose classification is valid and has intent `technical_fault`**, whatever the enrichment found (decided during spec review). With no customer, `check_outages` is the only tool with something to work on; the customer tools answer "no customer" as a result. For every other case, the step is skipped and the decision log says why.

### Input

One user message, inside tags as in the classifier, with the message escaped (`escapeMessage`):

- the **masked** message text and the channel;
- the classification: service type, area and summary;
- the enrichment: outcome, the found customer's ID, or the ambiguous candidates' IDs; the area and where it came from;
- the time the message was received (`received_at`), which is the "now" of every tool.

The enrichment's matching outages are **not** given, so the agent finds them with `check_outages`, and the evidence says which tool showed what.

### Tools

Three tools, read-only, defined with `strict: true` and validated with Ajv before running:

| Tool | Input | Returns |
| --- | --- | --- |
| `check_outages` | `area`, optional `service_type` | Outages in that area (compared as in enrichment: no case or diacritics) that cover `received_at`, plus those resolved in the 7 days before it: ID, service type, description, started, resolved. |
| `get_line_status` | `customer_id` | Per service of the customer: service ID, type, tariff, area, service status (`active` \| `terminated`), line state (`up` \| `degraded` \| `down`), state since, diagnostic. |
| `get_recent_tickets` | `customer_id` | The customer's tickets opened in the 90 days before `received_at`, newest first, at most 10: ID, service ID, category, summary, opened, closed. |

- **The customer-ID guard:** `customer_id` must be the found customer or one of the ambiguous candidates. Any other ID gets an error result ("not a customer of this case"). This keeps a message from steering the agent to someone else's data.
- **No identifier values** in any result: no customer number, contract number, phone or e-mail. Customer and service IDs are UUIDs.
- **Read-only by construction:** in PostgreSQL the tools run in a `READ ONLY` transaction; the eval uses the in-memory CRM.
- **Tool errors are results:** a bad input, an unknown tool, the guard or a database error goes back to the model as a `tool_result` with `is_error: true`, and is recorded.

### The loop

- **Model** `TRIAGE_MODEL` and effort `TRIAGE_EFFORT` by default, overridable with `INVESTIGATE_MODEL` and `INVESTIGATE_EFFORT`. Server-side fallbacks off, as for the P00 graders, so the stored model is the one that reasoned with the tools.
- **Step limit: 6 model turns** (`INVESTIGATE_MAX_TURNS`). Several tool calls in one turn are allowed and count as one turn; at most 12 tool calls in total.
- **Ends** when the model stops with a final answer, or at the limit. A turn that still asks for tools when the limit is reached ends with outcome `step_limit`.
- **The final answer** is structured output (`output_config.format` with the investigation schema, combined with the tools), validated with Ajv:

  ```json
  {
    "likely_cause": "area_outage",
    "confidence": 0.9,
    "summary": "An ongoing mobile outage in Opava covers the time of the message; the customer's mobile line is down since then.",
    "evidence": [
      { "tool": "check_outages", "finding": "Outage <id> (mobile, Opava) started 2026-11-06 07:47, not resolved." },
      { "tool": "get_line_status", "finding": "Service <id> (mobile) down since 2026-11-06 07:50." }
    ]
  }
  ```

  - `likely_cause`: one of the causes below.
  - `confidence`: 0–1.
  - `summary`: English, at most 400 characters.
  - `evidence`: 1–5 items for a cause other than `inconclusive` (0–5 for `inconclusive`); each names a tool and a finding of at most 300 characters.
  - **Checked in code** after the schema: every evidence item's tool must have been called successfully in this loop. Evidence from a tool that wasn't called makes the output invalid.

### Likely causes

Decided during spec review. A fixed list, in `src/taxonomy.ts`:

| Cause | Meaning | Typical evidence |
| --- | --- | --- |
| `area_outage` | A known outage of the service type in the customer's area covers the time of the message. | `check_outages`, often with the line down. |
| `line_fault` | Our side: the line is down or degraded, and no outage explains it. | `get_line_status`, perhaps a recent ticket. |
| `customer_equipment` | Our side looks fine: the line is up and no outage applies, so the problem is likely the customer's device or setup. | `get_line_status` (up), `check_outages` (none). |
| `service_inactive` | The service isn't active: terminated, or the number moved to another customer. | `get_line_status` (service status). |
| `inconclusive` | The tools don't show a cause, for example no customer and no outage. | |

### Outcomes and review

Each attempt has an **outcome**: `valid`, `step_limit`, `invalid` (output failed the schema or the evidence check, a refusal, or max tokens) or `error` (the API call failed).

Decided during spec review: **the case goes to review** (`investigation_inconclusive`) when any of these holds:

- the outcome isn't `valid`;
- the cause is `inconclusive`;
- the confidence is below **0.7** (`REVIEW_CONFIDENCE_THRESHOLD`, the same as for classification).

The investigation never changes the team, and never removes another reason code. So it can add reviews but can't lower recall on must-review.

### Retries

As for classification (P08): every attempt is stored before anything else happens. A transient API error on a non-final job attempt throws `TransientModelError` and the job retries; on the final attempt the `error` attempt is used and the case goes to review. A retry reuses the latest stored attempt for the same enrichment when its outcome is `valid`, `step_limit` or `invalid`, so a paid investigation never runs twice.

### The seed (`crm-generate.v2`)

- Every service gets a line-status row: `up` since its start date, unless the design says otherwise.
- Each of the 17 `technical_fault` messages gets an `expected.likely_cause`, and the line status and tickets are generated to support it:
  - found customer + an ongoing outage of its service type in its area → `area_outage` (line `down` since the outage started);
  - no identifiers + an ongoing outage in the message's area → `area_outage`;
  - msg-071 (found, no outage) → `line_fault` (line `down`, plus an open ticket on that service);
  - msg-069 (the number moved, the old service terminated) → `service_inactive`;
  - no identifiers and no ongoing outage (including a resolved one, or one of another service type) → `inconclusive`.

  That gives 8 `area_outage`, 1 `line_fault`, 1 `service_inactive` and 7 `inconclusive`. The list is reviewed by hand during implementation (decided during spec review).
- The expected enrichments don't change; a unit test checks it.

## Evaluation

`npm run eval:investigate -- [--from <run-dir>] [--subset small]`, under the paid-run guard (dry run, confirmation, cost cap), like `npm run eval`.

- **Input** (decided during spec review): the classifications stored in a classify run, by default the kept `classify.v2` run. Each labelled `technical_fault` message is masked and enriched against the in-memory seed, as the routing metrics do, then investigated. Only the agent is paid for. A message the run didn't classify as `technical_fault` is listed as "not investigated" and counts as a miss.
- **Labels:** the seed's `expected.likely_cause`.
- **Metrics,** overall and per language: cause accuracy, per-cause precision and recall, a confusion matrix, the share of cases sent to review by the investigation, outcomes (`valid`, `step_limit`, `invalid`, `error`), turns and tool calls per investigation (mean, max, step-limit hits), how often each tool was called, tool errors, cost and latency.
- **Output:** `eval/results/<run-id>/` as for `npm run eval` (`run.json` with model, effort, prompt and code versions, the input run's ID, seed hash and git commit; `outputs.jsonl`; `metrics.json`; `report.md`; `report.html`). `npm run eval:report` recomputes it from the stored outputs; `npm run eval:keep` keeps it.

## Decisions

### Requirements

| Decision | Choice | Why |
| --- | --- | --- |
| Line status source | A new seeded table `crm_line_status`, generated with a design per fault | The tools must find something an outage alone wouldn't show. The pipeline and the eval read the same data. Decided during spec review. |
| Causes | `area_outage`, `line_fault`, `customer_equipment`, `service_inactive`, plus `inconclusive` | Each cause has evidence a tool can show. A fifth cause with no tool behind it would be a guess. Decided during spec review. |
| When it runs | Every valid `technical_fault`, with or without a found customer | Outage evidence still helps the reviewer when the customer is unknown. Decided during spec review. |
| Inconclusive | Outcome not `valid`, cause `inconclusive`, or confidence below 0.7 | The same caution as for classification. Decided during spec review. |
| Expected causes | Designed in the seed by the generator, reviewed by hand | Deterministic and checked by a test, like the expected enrichments. Decided during spec review. |
| Customer-ID guard | Tools accept only the case's found or candidate customer IDs | Untrusted input mustn't be able to point the agent at other customers' data. |
| Evidence check | Every evidence item must name a tool that was called successfully | Evidence must come from the tools, not from the message or the model's guess. |

### Plan

| Decision | Choice | Why |
| --- | --- | --- |
| LLM client | A second method on the client in `src/llm/client.ts` for multi-turn calls with tools | Shares the error mapping, status codes and usage with the classifier. The loop is tested with a scripted mock. Decided during spec review. |
| Model and limit | `TRIAGE_MODEL`/`TRIAGE_EFFORT` by default (overridable), 6 turns | Three tools plus room to recover from a tool error and answer. Decided during spec review. |
| Decision log | Always an `investigate` entry; `skipped` when the case isn't a fault | Every new case has the same five steps. Decided during spec review. |
| Final answer | Structured output combined with strict tools | The API accepts `output_config.format` together with tools, so the answer is validated like the classifier's (checked in the Claude API docs). |
| Fallbacks | Off | The stored model must be the one that called the tools. |
| Routing input | `route()` takes the investigation, or `null` when none was run | The eval's classify-only routing metrics pass `null` and give the same results as `route.v2`, so the kept reports still reproduce. In the database path, routing a valid technical fault without an investigation is an error, so the pipeline can't skip it. |

### Validation

| Decision | Choice | Why |
| --- | --- | --- |
| Eval input | The kept `classify.v2` outputs, enriched against the seed | Realistic input; no reclassification is paid for. Decided during spec review. |
| Paid runs | The full 17 (~$0.70) and one demo (~$0.05), each after asking | Cause accuracy needs all 17; 3 can't show it. Decided during spec review. |
| Extra automated tests | Read-only tools; no identifier value in any request; the dataset-wide routing test with `route.v3` | Decided during spec review. |

## Notes

- **`customer_equipment` has no dataset example.** Only one fault message (msg-071) has a found customer and no outage, and it is designed as `line_fault`. `customer_equipment` is covered by loop and tool tests with fixtures only. With 17 messages and 1 example each of `line_fault` and `service_inactive`, per-cause numbers are indicative, and the report says so. New messages would need the P00 procedure (paid generation and grading), so they are not part of this phase.
- **Overlap with `customer_unidentified`.** The 9 faults with no identifiers already go to review (P07). The investigation adds evidence for the reviewer, and for some of them a second reason.
- **The seed hash changes** (`crm-generate.v2`). The kept runs record the old hash. Plan 3.4 checks that `eval:report` still reproduces them; if it doesn't, implementation stops and raises it.
- **Earlier tests that change:** the decision-log tests (four steps become five), `route.v2` → `route.v3`, `process.v1` → `process.v2`, the crm generator and seed tests, and the review screen tests.
- **Docs consulted:** the Claude API structured-outputs page (JSON outputs combined with strict tool use), through Context7.

## Implementation notes

- **The designed cause is `messages[].expected_cause`, not `expected.likely_cause`.** The dataset-wide enrichment test compares `expected` with the enrichment result as a whole, so the cause sits next to it (null for other intents).
- **`crm-generate.v2` adds line status in a last step with its own RNG** (`LINE_STATUS_SEED`). Everything `crm-generate.v1` wrote is byte for byte the same; the one new row is msg-071's open fault ticket. A test compares the reference check over the seed with each designed cause.
- **The tools read through a separate `InvestigationCrm` interface** (`src/pipeline/investigation-crm.ts`), implemented by both CRMs, instead of new `CrmLookup` methods (plan 2.4): enrichment's interface stays as it was.
- **`isInconclusive` lives in `src/pipeline/route.ts`**, not `investigate.ts` (plan 5.3): the review decision belongs with the routing rules, and it avoids an import cycle over the confidence threshold.
- **A case names its investigation through the decision log** (`investigate` entry, `investigation_id`); `cases` has no new column. A later `npm run investigate` stores a new attempt but can't change what a case shows. The `investigate` entry is written whenever an `enrich` one is, so a case with an invalid classification still has three entries.
- **`route()` takes an optional investigation.** Absent or null gives `route.v2`'s result, which the classify-only eval scoring uses; `routeInteraction` refuses a valid technical fault without one ("investigate first").
- **`apiStatus` is carried over from the attempt** by `runInvestigation`: it isn't stored (as for classifications), and an integration test caught that the runner otherwise never retried a transient agent error.
- **Assistant turns are passed back unchanged** (`converse` returns the raw content blocks): with thinking on, they carry signatures the API checks.
- **The kept classify reports were recomputed** (`eval:report`): only the router version (`route.v3`) and the seed hash changed; every number is the same (plan 8.4).
- **The step-name column of the decision log** is 11 characters wide now (`investigate`), in `npm run route`, `npm run process` and the review screen.

## Results (recorded during implementation)

- **Tests:** 864 unit tests and 204 integration tests pass locally.
- **Evaluation** (kept: `eval/results/kept/20261119-162816-investigate-full-claude-opus-5-5-investigate.v1/`), `claude-opus-5-5` at effort low, from the kept `classify.v2` run. Cost **$0.36** for 17 faults (estimate $1.15 before caching; the spec guessed ~$0.70).

  | Metric | Value |
  | --- | --- |
  | Cause accuracy | **16 / 17 (94.1%)** |
  | `area_outage` | 8 / 8 |
  | `line_fault` | 1 / 1 (msg-071) |
  | `inconclusive` | 7 / 7 |
  | `service_inactive` | 0 / 1 (msg-069 answered `inconclusive`) |
  | Outcomes | 17 valid; no step limit, invalid output or API error |
  | Turns | mean 2.0, max 3 |
  | Tool calls | mean 1.9, max 4; `check_outages` 17, `get_line_status` 9, `get_recent_tickets` 6; no tool errors |
  | Sent to review by the investigation | 8 of 17 (the 7 inconclusive and msg-069) |
  | Cost and latency | $0.021 and 6.2 s per fault |

  **msg-069, the one miss**, is arguably the safer answer. The phone number matched two customers; the agent looked up both, saw an active line for one and a terminated service for the other, and answered `inconclusive` (0.3): "a person should confirm which account it is". The designed label assumes the caller is the customer whose service was terminated. The case goes to review anyway (`customer_ambiguous`). Per-cause numbers are indicative only: two causes have one example each, and `customer_equipment` has none.
- **Demo** on a separate `triage_demo` database (Redis database 1, API on port 3001), after `crm:seed`; dropped and flushed afterwards. msg-071 posted through the API and processed with `npm run process` for **$0.044** ($0.020 classification, $0.024 investigation): `line_fault` at 0.8 in 2 turns, calling `get_line_status`, `check_outages` and `get_recent_tickets` in the first turn; the case was auto-routed to `technical_support` with five decision-log entries, and the review screen (`--spot-check`) showed the cause, evidence and tool calls.
